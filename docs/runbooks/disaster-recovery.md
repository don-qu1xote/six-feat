# Runbook — потеря Postgres

Восстановление после потери или порчи данных в Postgres. Механизм —
SF-INF-08 (`scripts/backup-postgres.sh` / `scripts/restore-postgres.sh`),
проверка механизма — SF-INF-09 (`scripts/dr-drill.py`).

> **[SF-DOC-08] Что это на самом деле сегодня.** Прода нет: единственная среда —
> машина автора (SF-INF-10), и база, о которой идёт речь ниже, — **локальный
> Postgres в контейнере на этой машине**. Значит: пользователей, которые
> заметят простой, нет; трафика, который надо «возвращать», нет; данные — те,
> что вы сами накликали и нафетчили. Документ настоящий и процедура рабочая,
> но масштаб последствий надо держать в голове, читая слова «инцидент» и
> «дежурный».
>
> Числа RPO/RTO (`docs/DEVELOPMENT.md`, «Backup & restore») — **цели, а не
> замеры**: они выведены из механизма и одного синтетического прогона, ни
> одного реального восстановления боевых данных не было и быть не могло.
> Ориентировочно: теряется до интервала бэкапа (по умолчанию сутки),
> `pg_restore` идёт порядка минуты на гигабайт.

> Роли ниже — заглушки: у проекта один владелец, и «дежурный» с «go/no-go» —
> это один и тот же человек. Таблица оставлена как форма для будущего, а не
> как описание существующего процесса.

| Роль | Кто | Отвечает за |
|---|---|---|
| Дежурный | владелец репозитория | шаги 1–5 |
| Go/no-go | владелец репозитория | шаг 6: возврат трафика |

---

## 0. Это точно потеря данных?

Реплика (`postgres-replica`, SF-INF-02) **не спасает** от потери данных:
`DELETE`, неудачная миграция и `DROP TABLE` доезжают до standby за
миллисекунды. Но и не всякий сбой — потеря данных.

| Симптом | Это не потеря данных |
|---|---|
| `/readyz` отдаёт 503, база жива | сначала проверьте пул соединений и диск |
| Postgres не стартует, данные на диске целы | сначала попробуйте поднять как есть |
| Диск заполнен | освободите место; restore тут не нужен |

Восстановление из дампа **перезаписывает** базу и стоит вам всех записей
после последнего бэкапа. Это последнее средство, а не первое.

## 1. Оповестить

1. Сообщить владельцу: что видно, с какого времени, какие сервисы задеты.
2. Зафиксировать **время начала инцидента** — от него считается фактический
   RTO и объём потерянных данных.
3. Не выполнять `restore` в одиночку без уведомления: шаг 6 требует второго
   человека, если он есть.

## 2. Остановить запись

Пока приложение пишет в повреждённую базу, точка восстановления уезжает.

```bash
ENV_PROFILE=prod docker compose stop six-feat six-feat-enrichment six-feat-game
```

`postgres` и `nginx` не трогаем: первый нужен для восстановления, второй
продолжит отдавать понятную ошибку вместо оборванных соединений.

## 3. Найти последний бэкап

```bash
# Локальный том (BACKUP_HOST_DIR, по умолчанию ./.backups)
ls -lt .backups/six-feat-*.dump | head

# S3-совместимое хранилище, если настроено (BACKUP_S3_URL)
aws --endpoint-url "$BACKUP_S3_ENDPOINT" s3 ls "$BACKUP_S3_URL/" | sort | tail
```

Имена — UTC-таймстемпы, поэтому лексикографическая сортировка = хронологическая.
Берите **самый свежий**, рядом с ним должен лежать `.sha256`.

Если свежий дамп битый — берите предыдущий: их хранится `BACKUP_KEEP`
(по умолчанию 7). Потеря данных вырастет на сутки за каждое поколение назад.

## 4. Проверить дамп ДО восстановления

Никогда не восстанавливайте непроверенный архив поверх живой базы: если он
битый, вы останетесь без обеих копий.

```bash
./scripts/restore-postgres.sh .backups/<dump> --dry-run
```

`--dry-run` сверяет `.sha256`, читает весь TOC архива и печатает план
(куда, сколько строк будет перезаписано), ничего не меняя.

## 5. Восстановить

Сначала — в **отдельную** базу, не поверх боевой. Так у вас остаётся
возможность сравнить и откатиться.

```bash
./scripts/restore-postgres.sh .backups/<dump> \
  --target-db six_feat_restored --create --yes-i-am-sure
```

Затем автоматическая проверка целостности — та же, что гоняет ежемесячный
drill:

```bash
python3 scripts/dr-drill.py --dump .backups/<dump> --target-db six_feat_verify
```

Он падает, если таблиц не хватает, ключевые пусты, нарушена ссылочная
целостность или не проходит smoke-запрос графа. **Красный drill — стоп:
дальше не идём, берём предыдущее поколение (шаг 3).**

Ручная сверка сверх этого:

```sql
SELECT count(*) FROM artists;
SELECT count(*) FROM credits;
SELECT max(last_fetch_ts) FROM fetch_state;  -- насколько свежи данные
```

`max(last_fetch_ts)` показывает фактическую точку восстановления —
именно это число идёт в постмортем как реальный RPO.

## 6. Go/no-go на возврат трафика

Решение принимает владелец. Условия:

- [ ] drill из шага 5 — зелёный;
- [ ] счётчики строк — того же порядка, что до инцидента;
- [ ] `max(last_fetch_ts)` соответствует ожидаемому возрасту бэкапа;
- [ ] известно и записано, сколько данных потеряно.

Только после этого переключаем боевую базу и поднимаем сервисы:

```bash
./scripts/restore-postgres.sh .backups/<dump> --yes-i-am-sure   # в DB_NAME
ENV_PROFILE=prod docker compose up -d
curl -fsS http://<host>:8080/readyz
```

`/readyz` должен отдать `{"status":"ready"}`. Пока он 503 — трафик не пускаем.

## 7. После инцидента

1. Записать фактические RTO и RPO и сравнить с целями в `DEVELOPMENT.md`
   (там цели, а не замеры — первый настоящий прогон их и уточнит);
   если они разошлись — исправить документ, а не память.
2. Убедиться, что расписание бэкапов живо:
   `docker compose --profile backup ps`.
3. Удалить временные базы: `six_feat_restored`, `six_feat_verify`.

## Ежемесячный drill

`.github/workflows/dr-drill.yml` запускает `scripts/dr-drill.py` первого
числа каждого месяца: восстанавливает последний реальный дамп в чистый
Postgres и проверяет данные. Красный прогон означает, что этот ранбук
сейчас не сработает — чинить нужно до инцидента, а не во время.

Если `BACKUP_S3_URL` не настроен, прогон брать неоткуда: workflow снимает
свежий дамп со своей тестовой базы и проверяет на нём **сам механизм**,
явно помечая, что реальный бэкап не проверялся. Это честный сигнал
«проверено не то», а не зелёная галочка.
