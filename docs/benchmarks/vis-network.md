# SF-WEB-76: замер перед заменой vis-network

Тикет предлагал заменить `front/vendor/vis-network.min.js` собственным
рендерером и просил сначала померить, а потом решать. Ниже — замеры и
рекомендация.

**Вывод: сейчас не заменяем.** Библиотека действительно дорогая, но дорога
она загрузкой, а не отрисовкой, и почти весь этот вес снимается отложенной
загрузкой в десять строк — без тысячи строк своего рендерера. Подробности и
цифры ниже; отдельно отмечено, что именно изменит решение.

## Что осталось за библиотекой

После SF-API-21 (раскладка на сервере) и SF-API-22 (контуры на сервере)
инвентаризация по коду `front/src`:

| Уже наше | Ещё библиотечное |
| --- | --- |
| рёбра — `edge-render.js` рисует их сам, библиотечные скрыты `suppressNativeEdgeColor` | холст, DPR, `autoResize` |
| контуры групп — `bubble-contours.js` | камера: зум, панорама, `fit`, `moveTo`, `focus`, `DOMtoCanvas` |
| подсветка и цвета — `highlight.js` | отрисовка узла: круг, фото по клипу, рамка, свечение |
| тултипы — `tooltips.js` | события: 8 штук (см. ниже) |
| геометрия и позиции — сервер | hit-testing (`getNodeAt`), перетаскивание узла |
| | `vis.DataSet` — реактивное хранилище |

События, на которые кто-то подписан: `click`, `doubleClick`, `hoverNode`,
`blurNode`, `dragStart`, `dragging`, `dragEnd`, `zoom`. Плюс `beforeDrawing`
— в него встроена вся наша отрисовка (10 подписок).

Подписей у узлов нет вообще: `nodeVisual` не задаёт ни `label`, ни `font`.
Это заметно упрощает возможную замену — вёрстка текста обычно и есть самая
громоздкая часть рендерера узлов.

## Вес

| | байт | gzip -9 |
| --- | ---: | ---: |
| `vendor/vis-network.min.js` | 688 911 | 161 713 |
| `dist/script.js` — весь наш фронтенд, esbuild `--minify` | 216 129 | 62 612 |
| **итого JS страницы** | **905 040** | **224 325** |

Библиотека — **72% всего JS** и в 2,6 раза тяжелее всего рукописного кода
вместе взятого. Оба скрипта в `index.html` подключены без `defer`.

## Загрузка

Chromium 147 headless, `--disable-gpu`, раздача с localhost. Троттлинг CPU
через CDP `Emulation.setCPUThrottlingRate` — грубая замена телефона, а не
замер на устройстве.

Скачивание + разбор + исполнение `vis-network.min.js`, три прогона:

| CPU | мс |
| --- | --- |
| 1× | 55, 57, 59 |
| 4× | 197, 213, 213 |
| 6× | 263, 265, 318 |

Загрузка лендинга целиком (viewport 390×844, внешние шрифты убраны, чтобы не
заслоняли собой замер), медиана из двух прогонов, `loadEventEnd`:

| CPU | со скриптом vis | без него | разница |
| --- | ---: | ---: | ---: |
| 1× | 90 / 99 мс | 46 / 58 мс | −44 / −41 мс |
| 4× | 382 / 424 мс | 205 / 210 мс | −177 / −214 мс |

**Половина времени загрузки лендинга — это библиотека, которая на лендинге не
нужна.** Графа там ещё нет, первый `vis.Network` создаётся только после
поиска. И это при нулевой сетевой задержке; на реальном канале сверху ляжет
передача 161 КБ.

Создание самого `vis.Network` на 300 узлов — отдельные 54–67 мс при 1×,
300 мс при 4×, 477 мс при 6×. Это цена каждого нового поиска, а не только
первой загрузки.

## Кадр

Граф из N узлов и ~1,4·N рёбер, 120 кадров панорамы с зумом, темп задаёт
`requestAnimationFrame`, по одной отрисовке на кадр у обоих. Время меряется
внутри самой отрисовки: у библиотеки — между `beforeDrawing` и
`afterDrawing`, у прототипа — вокруг функции `draw`. Прототип рисует то же
самое: те же рёбра тем же кодом, круг с фото по клипу, рамка, свечение.

Медиана мс на кадр (в скобках p95), два независимых прогона:

| узлов | vis | свой прототип |
| ---: | --- | --- |
| 150 | 1,2 (2,2) / 1,2 (2,3) | 0,7 (1,1) / 0,7 (1,1) |
| 300 | 2,0 (3,2) / 2,5 (12,0) | 1,3 (1,6) / 1,4 (2,4) |
| 600 | 3,9 (7,5) / 4,8 (9,8) | 2,3 (3,9) / 2,3 (3,9) |
| 900 | 5,5 (13,1) / 6,2 (11,5) | 3,4 (4,6) / 3,8 (4,8) |

Свой рендерер в 1,6–1,8 раза быстрее и заметно ровнее: отношение p95 к
медиане у него ~1,4, у библиотеки 1,8–2,4.

**Но выигрыш этот некуда девать.** Бюджет кадра — 16,7 мс, и библиотека
укладывается в него с запасом даже на 900 узлах. Типичный граф намного
меньше: `GRAPH_DEFAULT_LIMIT = 40`, порог «большого графа» в коде —
`LARGE_GRAPH_NODE_THRESHOLD = 150`. То есть производительность отрисовки
поводом для замены не является — ни сегодня, ни на графах вчетверо больше
типичного.

## Физика перетаскивания

Тикет допускал вывод «физика перетаскивания стоит этих килобайт». Проверено
отдельно: пять узлов, три из них `fixed: {x: true, y: true}` и наложены друг
на друга, два свободных и тоже наложены; включается физика с боевыми
настройками солвера (`barnesHut`, те же константы, что в `networkOptions`) на
1,2 секунды.

Смещение: закреплённые — **0,000 px**, свободные — 99 и 102 px.

А `_flyToLayout` в `physics.js` по завершении вылета закрепляет **все** узлы
графа (`fixAll`). Значит `nudgePhysics(PHYSICS_EXPAND_MS)` на `dragEnd`
(`events.js:230`) сегодня не двигает ничего — это холостой прогон солвера.
Единственное место, где физика ещё работает, — `_degradeWithoutLayout`, откат
на случай, когда запрос раскладки не удался: он сначала снимает закрепление.

Платить килобайтами за физику перетаскивания не приходится: её уже нет.

## Сколько стоила бы замена

Оценка по инвентаризации, в строках нашего обычного стиля:

| часть | строк |
| --- | ---: |
| холст, DPR, ресайз | ~80 |
| камера: зум к курсору, панорама, `fit`, `moveTo`, `focus`, плавность | ~220 |
| отрисовка узла: круг, клип фото, рамка, свечение, запасная картинка | ~150 |
| хранилище с API `DataSet` (36 мест вызывают `update`) | ~120 |
| ввод: клик, двойной клик, hover, перетаскивание, тач, щипок | ~260 |
| hit-testing с пространственной сеткой | ~90 |
| склейка, чтобы `vis-adapter/index.js` не изменился | ~120 |
| **итого** | **~1040** |

Это меньше, чем 1500–2000 из тикета, — потому что рёбра, контуры, тултипы,
подсветка и вся геометрия уже свои. Но строки распределены неудачно: четверть
из них — ввод с тачем и щипком, то есть ровно то, что vitest проверяет хуже
всего и что ломается у пользователя, а не в CI.

## Рекомендация

**Не заменять. Вместо этого отложить загрузку библиотеки** до момента, когда
граф действительно понадобится (первый `initNetwork`).

Почему так:

1. Единственная измеренная боль — блокирующая загрузка на лендинге, где граф
   не показывается: −44 мс при 1× и −177…−214 мс при 4×, то есть половина
   времени загрузки. Это проблема **загрузки**, а не рендерера, и решается
   она отложенной загрузкой примерно в десять строк.
2. Отрисовка не тормозит: 5,5 мс на кадр при 900 узлах против бюджета в
   16,7. Своя была бы вдвое быстрее, но эти 2–3 мс некуда потратить.
3. После отложенной загрузки от полной замены остаётся: те самые 2–3 мс на
   кадр на графах, которых у нас не бывает, и минус одна зависимость. За
   ~1040 строк, из которых 260 — жесты на тач-экране. Размен невыгодный.
4. То, что могло бы перевесить — физика перетаскивания, — измеримо мертво.

Что изменит решение (тогда стоит вернуться к тикету):

- графы регулярно перевалят за ~900 узлов, и p95 кадра начнёт задевать 16,7 мс;
- у библиотеки появится уязвимость или она перестанет собираться — 688 КБ
  чужого кода без обновлений;
- понадобится отрисовка, которой в библиотеке нет и которую неудобно
  пристроить в `beforeDrawing`.

Отложенная загрузка ничего из этого не закрывает, но и не мешает: она не
меняет ни одной строчки в `vis-adapter/`, и полная замена после неё делается
ровно так же, как делалась бы сейчас.

## Как воспроизвести

Замеры сняты внешним стендом (Playwright + Chromium из `/opt/pw-browsers`),
в репозиторий он не добавлен — это разовая проверка, а не то, что должно
гоняться в CI. Чтобы собрать заново:

1. Статическая страница с `vis-network.min.js`, граф из N узлов с
   аватарками-заглушками в `data:`-URI (сеть в замере не участвует),
   позиции расставлены по хабам заранее.
2. Вес: `gzip -9 -c` по `vendor/vis-network.min.js` и по сборке
   `npx esbuild src/main.js --bundle --minify`.
3. Загрузка: `Emulation.setCPUThrottlingRate` через CDP, два варианта
   страницы — со `<script src="/vendor/vis-network.min.js">` и без него,
   сравнение `loadEventEnd` из Navigation Timing. Внешние ссылки на шрифты
   надо убрать: иначе они дают 12 секунд и заслоняют всё остальное.
4. Кадр: 120 кадров по `requestAnimationFrame`, `moveTo({animation: false})`
   на каждом; у библиотеки время между `beforeDrawing` и `afterDrawing`, у
   прототипа — вокруг `draw`. Счётчик отрисовок обязателен: без него легко
   сравнить один кадр библиотеки с двумя кадрами прототипа.
5. Физика: пять узлов, три закреплённых и наложенных, два свободных и
   наложенных; `setOptions({physics: {enabled: true}})`, через 1,2 с сравнить
   `getPositions()` с исходными.

## Оговорки

- Числа сняты в headless-Chromium на x86-64 в контейнере с `--disable-gpu`.
  Абсолютные значения на живом железе будут другими; сравнение «библиотека
  против прототипа» и «с ней против без неё» — устойчиво, оба варианта
  меряются в одинаковых условиях и в двух прогонах дают одно и то же.
- Троттлинг CPU 4×/6× — не замена замеру на телефоне. Он показывает порядок,
  а не то, что увидит конкретный пользователь.
- Прототип рендерера — прототип. Он рисует то же содержимое, но у него нет
  ни событий, ни настоящего hit-testing, ни анимаций камеры. Его цена кадра
  — нижняя граница, а не то, что получилось бы в итоге. Разрыв в 1,6–1,8
  раза следует считать оптимистичным для замены.
