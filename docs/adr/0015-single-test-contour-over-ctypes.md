# ADR-0015: Один тестовый контур — C++ проверяется из pytest через ctypes, gtest убран

## Статус

Принято (Release 1.4). Записано задним числом: решение уехало в коммит
`8196f2b`, названный по другому тикету, без своего номера и без ADR.

## Контекст

До Release 1.4 бэкенд проверялся двумя независимыми контурами:

- **gtest + CMake** — `services/six-feat/tests/unit/`, отдельная джоба CI,
  `FetchContent` тянул googletest v1.15.2 с GitHub на каждый прогон;
- **pytest** — всё остальное: ручки, база, контракты, моки.

Два раннера означали две истории покрытия, два способа завести тест и два
места, куда смотреть при падении. Плюс `FetchContent` — сетевая зависимость в
джобе, которая без сети не собирается вовсе.

Отдельный повод пересмотреть форму дали SF-API-21 и SF-API-22: геометрия
раскладки и контуров переехала в C++ из браузера, и её надо было проверять
эталонными векторами, снятыми с прежней реализации. Вопрос «каким
инструментом» встал заново на свежем коде, а не на легаси.

## Решение

1. **gtest удалён целиком** — `services/six-feat/tests/unit/` вместе с
   `CMakeLists.txt`, фейками и `FetchContent`.
2. **Чистые библиотеки собираются в `.so` и зовутся из pytest.**
   `tests/native/loader.py` компилирует `libs/six-feat-layout` и
   `libs/six-feat-image` с `--coverage` и загружает через `ctypes`;
   `tests/native/bridge.cpp` — плоский C-ABI поверх них, который ничего не
   считает, только раскладывает массивы из Python в структуры и обратно.
3. **Тесты — обычные питоновые файлы**: `tests/test_layout_geometry.py`,
   `tests/test_contours.py`, `tests/test_dominant_color.py`. Эталонные
   векторы, снятые с браузерной реализации, переехали в них как данные.
4. **Покрытие C++ снимается тем же прогоном.** `.gcda`, которые оставляет
   процесс pytest, читает `scripts/check-cpp-coverage.py` с гейтом
   `--min 80` в джобе `unit-tests-cpp`.

## Последствия

**Что стало лучше.** Один раннер, одна история покрытия, один способ завести
тест на бэкенде. Сетевой зависимости в джобе больше нет — нужен только `g++`.
Покрытие C++ стало измеряемым и гейтованным (на момент решения — 94% при
пороге 80), чего у gtest-контура не было вовсе.

**Чем за это заплачено — и это главное в решении.** Глубина C++-тестирования
разменяна на единообразие контура, и размен неравноценный:

- через `ctypes` проверяется только то, что вынесено в C-ABI. Всё, что не
  прошло через `bridge.cpp`, не проверяется никак — а протащить туда классы,
  шаблоны или что-то с нетривиальным временем жизни несравнимо дороже, чем
  написать `TEST_F`;
- `bridge.cpp` — код на C++, который сам ничем не покрыт и в счёт покрытия
  намеренно не входит. Ошибка в нём выглядит как ошибка в библиотеке;
- маршалинг написан руками, и рассогласование `argtypes` с сигнатурой не
  ловится компилятором — только падением или, хуже, тихой порчей памяти;
- покрыт таким образом может быть только код без userver: сервисные классы
  (хендлеры, компоненты) остаются проверенными исключительно через HTTP.

**Когда решение стоит пересмотреть.** Если появится чистая библиотека с
API сложнее «массивы на входе, массивы на выходе», или если ошибка в
`bridge.cpp` хоть раз будет диагностирована как ошибка в библиотеке —
дешевле вернуть gtest для этой библиотеки, чем растить переходник.

**Что решение не решает.** Оно не про сервисный код: `services/*/src`
как проверялся только через pytest по HTTP, так и проверяется.
