# ADR-0014: Одна декларативная схема вместо версионированных миграций

## Статус

Принято (SF-DOC-08, Release 1.3). Записано задним числом: решение уехало в
коммиты `08b12cc`, `41d1378` и `8196f2b` без своего тикета и без ADR, а
объяснить его через год будет нечем.

Опирается на [ADR-0012](./0012-six-feat-as-sole-public-entry.md) (six-feat —
единственный, кто ходит в базу) — не заменяет его.

## Контекст

До Release 1.3 схема жила версионированными файлами `postgresql/migrations/
V1__initial_schema.sql` … `V11__drop_yandex_artifacts.sql`. Форма стандартная
и правильная — ровно для того случая, ради которого её изобрели: есть
работающая установка с данными, которые нельзя потерять, и накатывать
изменения на неё надо по шагам.

Такой установки у проекта нет и не было. Прод — локальная машина автора
(`make deploy-local`), базу пересоздают, тесты поднимают её с нуля на каждый
прогон. Реестр версий обслуживал сценарий, которого не существует, и при этом
брал свою цену:

- каждое изменение схемы — новый файл, и вопрос «а какая схема сейчас?»
  требовал прочитать одиннадцать файлов подряд и сложить их в голове;
- `V11__drop_yandex_artifacts.sql` — миграция, отменяющая миграцию, ради
  базы, которая при следующем запуске всё равно создаётся заново;
- при откате Яндекса пришлось решать, «дописывать V12» или «править V10», —
  вопрос без правильного ответа, потому что мигрировать было нечего.

## Решение

1. **Схема — один идемпотентный список.** `kSchemaStatements` в
   `libs/six-feat-storage/src/persistent_store.cpp`: `CREATE TABLE IF NOT
   EXISTS`, `CREATE INDEX IF NOT EXISTS`. Приложение применяет его при
   старте, порядок версий не хранится нигде.
2. **`postgresql/schema.sql` — его зеркало** для инструментов, которым нужен
   SQL-файл, а не бинарник (например, джоба EXPLAIN).
3. **Паритет зеркал стережёт тест.**
   `tests/test_migrations.py::test_schema_statements_match_schema_sql`
   разбирает оба источника и сравнивает нормализованные операторы: разойтись
   молча они не могут.
4. **Возврат к версиям закрыт тестом.**
   `test_no_versioned_schema_files_remain` ищет `postgresql/**/V*__*.sql` по
   имени и падает, если такой файл появился, — в том числе пустой, что важно
   при применении патчей через `git apply`.
5. **Каталог `postgresql/migrations/` удалён.**

## Последствия

**Что стало лучше.** Схема читается за один заход и в одном месте. Изменение
схемы — правка двух зеркал, а не новый файл с порядковым номером. Откат
крупной функциональности перестал порождать миграции, отменяющие миграции.

**Чего это решение стоит — и это надо назвать прямо.** Проект потерял
способность накатить изменение на базу с данными. Не «усложнил» — потерял:
`CREATE TABLE IF NOT EXISTS` не добавит колонку к существующей таблице, а
`ALTER TABLE ... IF NOT EXISTS` в этот список сознательно не кладут (такая
строка появилась однажды в SF-API-23 и была убрана в `8196f2b` именно как
миграция по форме).

Пока установка одна и её пересоздают — цены нет. Как только появится хост с
данными, которые нельзя терять, реестр версий придётся вернуть, и это будет
отдельная работа, а не «дописать строчку». Сигнал, по которому это надо
делать, простой: первый раз, когда изменение схемы нельзя выкатить, удалив
базу.

**Что решение не решает.** Оно ничего не говорит про данные — только про
структуру. Переносом данных между версиями схемы по-прежнему никто не
занимается.
