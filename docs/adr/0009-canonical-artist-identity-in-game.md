# ADR-0009: Каноническая идентичность артиста в игре — реальный Genius id

## Статус

Принято (Ф0 сброса геймификации — фиксирует модель до переписывания
игрового фронта в Ф1). Парная к ADR-0008: та — про единый движок графа,
эта — про то, чем в игре идентифицируется артист.

## Контекст

Движок графа ключует всё на **числовых Genius id**: id узла, `from`/`to`
рёбер, `State.network.getPositions([id])`. Игровая модель
(`front/src/game/connect-model.js`, `connect.js`), наоборот, оперирует
**именами** артистов — их игрок вводит с клавиатуры или выбирает из
автокомплита.

Мост между двумя мирами сейчас — `synthId(name)` в
`front/src/game/game-board.js`: детерминированный **отрицательный**
хэш-id, который выдаётся любому имени, ещё не разрешённому в реальный id
(«negative so it can never collide with a real Genius id»). Это позволяет
узлу-имени отрисоваться до резолва, но плодит два класса проблем:

- Имя, которое **набрали, но не выбрали** из списка, остаётся
  неразрешённым. Код, которому нужен настоящий id (серверная анти-чит
  проверка через `/internal/neighbours`, публикация ежедневной пары в
  `services/game/admin_handler.cpp`), видит `id=0`/отсутствующий id и
  берёт случайную/неверную пару. Это корневая причина бага админки
  «Couldn't publish / случайная пара» и класса «набрано, но не выбрано».
- В игровом состоянии сосуществуют реальные и синтетические id — их нельзя
  без оговорок сравнивать, кэшировать или передавать на бэк.

При этом «одуванчик» (реальные коллабораторы фокуса) уже приходит из
`/api/v1/graph` с **настоящими** id (`front/src/game/game-graph.js`), и
серверный валидатор (`chain_validator`) тоже работает по реальным
данным — то есть половина системы уже канонична, а синтетические id живут
только на входном шве.

## Решение

**Реальный Genius id — каноничный ключ артиста в игре. Имя попадает в
игровое состояние только после того, как разрешено в реальный id.**

1. **Резолв на вводе, а не «когда-нибудь потом».** Каждый эндпоинт
   (старт/цель) и каждый хоп несёт разрешённый Genius id прежде, чем стать
   частью игрового состояния. Резолв происходит в момент выбора из
   автокомплита или явным шагом для набранного текста — не лениво по ходу
   рендера.
2. **`synthId()` удаляется.** В игровом состоянии нет синтетических id.
   Всё, что рисуется и отправляется на бэк, ключуется реальным id.
3. **«Набрано, но не разрешено» — заблокированное состояние с честной
   ошибкой** («выберите артиста из списка»), а не молчаливый `id=0` и не
   фейковый узел. Провал резолва (сеть / нет такого артиста) — тоже
   честное состояние, той же природы, что «no graph data» в
   `game-graph.js`.
4. **Админ-публикация и анти-чит всегда работают на реальных id** — по
   построению, раз других в состоянии не бывает.

## Последствия

**Плюсы:**
- Убирает корневую причину P1 (админка «случайная пара») и всего класса
  «набрано, но не выбрано» — одним изменением модели, а не заплатками на
  каждом call-site.
- Игра и движок согласны об идентичности: сравнение узлов, кэш фото/id,
  передача на бэк — без оговорки «а это может быть синтетический id».
- Ничего не ломает у «одуванчика» и валидатора — они уже на реальных id.

**Минусы / цена:**
- Игрок не может «протолкнуть» имя, которое не резолвится в реального
  Genius-артиста. Это, по сути, правильно: непроверяемого артиста всё
  равно нельзя засчитать анти-читом — но UX обязан честно объяснять блок,
  а не выглядеть как «не работает».
- Появляется зависимость от надёжности резолв-эндпоинта на вводе (частично
  уже есть — `resolveId` в `connect.js`); его отказ обязан всплывать
  честным состоянием, а не фейковым узлом.
- Физическое удаление `synthId()` и перевод входного шва на резолв — это
  работа Ф1/Ф2 (тикет SF-GAME-34), а не следствие самого принятия ADR.

## Дополнение 2026-08 (SF-ARCH-04/05/06, SF-GAME-23)

Принцип этого ADR **сохранён полностью**: резолв на вводе, никаких
синтетических id в игровом состоянии, честная ошибка вместо заглушки.
Расширилось только понятие «канонический id»: было «всегда Genius»,
стало «Genius, если известен; иначе идентичность собственного провайдера
(namespaced Yandex id)» — см. [ADR-0013](./0013-two-provider-artist-identity.md)
за полным обоснованием и связью с namespaced-id-пространствами.

Это НЕ тот же класс проблемы, что `synthId()` выше. `synthId()` был
временным, отрицательным, ничего не значащим числом для *ещё не
разрешённого* имени — ровно то, что этот ADR запретил. Namespaced Yandex
id — это реальный, стабильный, внешне проверяемый идентификатор от
реального провайдера (Yandex Music), присвоенный артисту, который уже
**разрешён**, просто в другом пространстве. Различие существенное:
`synthId()` кодировал «мы не знаем, кто это»; namespaced id кодирует «мы
точно знаем, кто это, по данным другого провайдера».

Практическое следствие для игры: `/internal/neighbours` (единственный
шов между игрой и графом) канонизирует id на чтении (см. ADR-0013) — игра
получает уже свёрнутые к одному id id пары, если связка `artist_alias`
для них существует. Полная канонизация id, попадающих в игровое
состояние по ДРУГИМ путям (админ-публикация дейли, пользовательский
`POST /challenge`), где сид/цель не проходят через `/internal/neighbours`,
пока НЕ реализована — это открытый пробел, а не забытый случай (см.
ADR-0013, раздел «Последствия»).

## Дополнение 2026-08 (снятие namespaced Yandex id)

Всё, что описано в «Дополнение 2026-08 (SF-ARCH-04/05/06, SF-GAME-23)» выше,
относилось к намеренно поддерживаемому Yandex-only пути, который был позже
полностью удалён (см. addendum к [ADR-0011](./0011-music-source-provider-abstraction.md)
и статус [ADR-0013](./0013-two-provider-artist-identity.md), теперь
архивного). Namespaced Yandex id, `artist_alias` и канонизация на чтении
в `/internal/neighbours` для них удалены вместе с остальной интеграцией.
Принцип этого ADR возвращается к исходной формулировке: **единственный
канонический id — реальный Genius id**, без «Genius, если известен;
иначе...» — второго id-пространства в системе больше нет.
