# ADR-0007: Выделение game в отдельный сервис

## Статус

Предложено (задел под §7 — игровой режим ещё не реализован; эта ADR
фиксирует направление, а не завершённое решение).

## Контекст

Проект готовится ввести игровой режим поверх уже существующего графа
коллабораций (см. ROADMAP, спринт S11 «Пред-игровой фундамент» и
последующие). В коде уже есть три независимых, реальных задела под это,
предшествующих самому игровому сервису:

- **SF-DB-06** (`libs/six-feat-common/src/enrichment/prune_task.hpp`):
  опциональный prune устаревших артистов добавлен заранее именно потому,
  что игровой режим ожидаемо резко увеличит объём и частоту сканирования
  графов коллабораций — неограниченный рост `artists`/`songs`/`credits`
  станет реальной проблемой хранения, которую сейчас снимать рано
  (`PRUNE_TTL_DAYS=0` по умолчанию), но механизм должен уже существовать.
- **SF-WEB-25** (`front/src/ui/router.js`): минимальный клиентский
  роутинг с явными поверхностями `#/graph`/`#/game` введён «перед вводом
  отдельного игрового режима» — сама игровая поверхность ещё не
  реализована, но URL уже адресует её как отдельное состояние.
- Комментарий в `services/six-feat/static_config.yaml` о JSON-логировании
  прямо ссылается на будущий пятый сервис: «этот блок должен оставаться
  идентичным во всех 4 (скоро 5, см. SF-GAME-10) сервисах».

Ни один из этих трёх заделов пока не объясняет, почему игровой режим
должен стать **отдельным сервисом**, а не фичей внутри `six_feat` — этот
аргумент эта ADR формулирует по аналогии с уже принятыми разрезами
(ADR-0001–0004), а не цитирует существующее решение.

## Решение (предварительное)

По аналогии с обоснованием ADR-0001–0004, игровой режим — кандидат на
отдельный сервис `six-feat-game` по тем же трём критериям:

1. **Профиль нагрузки отличается от чтения графа.** Игровая механика —
   вероятно stateful-сессии (раунды, очки, таймеры) поверх уже
   построенного графа, а не stateless HTTP-хендлеры графа/пути/поиска.
   Смешивание в одном процессе повторило бы проблему, которую уже решали
   для enrichment (ADR-0002): разный жизненный цикл, разная нагрузка,
   разная цена отказа.
2. **Внутренний контракт, а не прямой доступ к БД.** Как и
   genius-gateway (ADR-0003) и enrichment (ADR-0002), `six-feat-game`
   должен обращаться к графовым данным через internal HTTP API
   (`X-Internal-Secret`-gated), а не читать Postgres напрямую в обход
   `PersistentStore`/`ArtistRepository` — тот же паттерн, что уже
   используется всеми внутренними сервисами. Контракт-тесты по образцу
   SF-TST-01 (`tests/test_contract_gateway.py`) должны появиться и для
   этого контракта до того, как на нём будет что-то построено (см.
   ROADMAP: «Это страховка перед добавлением game↔six-feat
   internal-контракта»).
3. **Секретный/деплойный периметр отличается.** Игровой режим — не
   обязательно та же зона доверия, что чтение публичного графа
   коллабораций (возможна отдельная модерация, лимиты, история сессий) —
   отдельный сервис даёт то же преимущество изоляции секретов, что
   auth-сервис получил для `GENIUS_CLIENT_SECRET` (ADR-0004).

Открытые вопросы, которые эта ADR сознательно НЕ решает (предмет
последующих, более конкретных ADR/тикетов, когда появится реализация):
точная форма internal-контракта game↔six-feat, нужен ли игре собственный
Postgres-доступ или только чтение через six-feat, разделяет ли игра
Postgres-кластер с остальными сервисами (как enrichment) или это
отдельное хранилище.

## Последствия

**Плюсы (ожидаемые, по аналогии с ADR-0001–0004):**
- Игровая логика не рискует уронить или замедлить хендлеры чтения графа.
- Явный контракт с самого начала — не «сначала common-код, потом
  выделяем сервис задним числом», как исторически было с enrichment/
  genius-gateway (см. ADR-0002/0003 — обе начинались как in-process
  компоненты).

**Минусы / цена (ожидаемые):**
- Пятый сервис — пятый `docker-compose.yml` блок, пятый
  `static_config.yaml`, пятый Dockerfile target, пятая точка
  рассинхронизации портов/секретов (см. риски в ADR-0001).
- До появления реальной реализации это остаётся предположением, а не
  проверенным решением — статус «Предложено», не «Принято».
