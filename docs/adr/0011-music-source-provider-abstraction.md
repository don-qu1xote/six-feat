# ADR-0011: Абстракция MusicSourceProvider — Яндекс дефолт/обязателен, Genius — углубление и fallback

## Статус

Принято (SF-ARCH-02, Release 0.8). Опирается на
[ADR-0009](./0009-canonical-artist-identity-in-game.md) (каноническая
идентичность артиста) и [ADR-0001](./0001-split-into-four-services.md)
(разбиение на сервисы) — не заменяет ни одно из них.

## Контекст

До Release 0.8 единственным источником рёбер графа коллабораций был
Genius: `CollabService` ходил напрямую в `GeniusGatewayClient`, который
ходил в `six-feat-genius-gateway`. Genius API кредитует роли (primary/
producer/writer/featured), но у него собственные rate-limit'ы и
доступность — единственная точка отказа для *всего* графа, не только для
углублённых данных.

**Разворот 2026-07-27**: Яндекс.Музыка (реверс-инженеренный API,
`six-feat-yandex-gateway`, SF-YM-01) становится **дефолтным и обязательным**
источником рёбер для *дефолтного* графа — не опциональным дополнением "на
будущее". Причина: co-appearance артистов на треке Яндекс отдаёт дёшево и
без per-user OAuth (сервисный токен на весь деплой), тогда как Genius
несёт более богатую ролевую гранулярность (producer/writer/featured), но
дороже по rate-limit'ам и требует более тяжёлого клиента (уже
централизованного в genius-gateway). Разумно развести ответственность:
Яндекс — *ширина* графа (кто с кем вообще пересекался), Genius —
*глубина* (какая именно роль) плюс страховка на случай, если Яндекс
недоступен.

Технически нужна была абстракция, за которой CollabService не знает,
какой конкретно апстрим дал ребро — иначе логика fallback/переключения
размазалась бы по вызывающему коду, а не жила бы в одном месте.

## Решение

1. **Интерфейс `MusicSourceProvider`** (`libs/six-feat-common`):
   `GetCollaborationEdges(seed, user_token) → vector<ProviderEdge>`.
   `ProviderEdge{from, to, source, role}` — оба конца ребра уже
   **реальные Genius id** (см. «Явная связь с ADR-0009» ниже), `source`
   (`EdgeSource::YandexFeature`/`GeniusCredit`) — аудит-метаданные о том,
   КАКОЙ провайдер отдал ИМЕННО ЭТО ребро, не второй ключ идентичности.
2. **Два провайдера, оба реализуют интерфейс** (`services/six-feat/src/infrastructure`):
   `YandexMusicSourceProvider` (обёртка над `six-feat-yandex-gateway`,
   сервисный токен, `role` всегда `"feature"` — это всё, что физически
   даёт co-appearance) и `GeniusMusicSourceProvider` (обёртка над
   `GeniusGatewayClient`, полная ролевая гранулярность).
3. **Провайдер, который не может достучаться до апстрима (rate-limit,
   circuit open, сеть), БРОСАЕТ исключение**, а не молча возвращает пустой
   список — иначе "Яндекс сказал: рёбер нет" неотличимо от "Яндекс
   недоступен", а это два разных случая с разной обработкой.
4. **`MusicSourceProviderChain`** — компонент-композиция, пробует
   провайдеров по порядку из `static_config.yaml` (`providers:` список,
   дефолт `[yandex, genius-fallback]`), первый успех — результат; если все
   бросили — честно пробрасывает последнюю ошибку выше (`TryProvidersInOrder`,
   `libs/six-feat-common`, пер функция, юнит-протестирована в SF-TST-04
   фейками успешного/падающего провайдера без сети).
5. **Никакой новой колонки/enum `provider` в БД** — `ProviderEdge.source`
   существует только на уровне возвращаемых данных провайдера
   (presentation/observability), не персистится как часть идентичности
   артиста или связи.

### Явная связь с ADR-0009 — почему идентичность НЕ меняется

[ADR-0009](./0009-canonical-artist-identity-in-game.md) фиксирует: **реальный
Genius id — единственный канонический ключ артиста, везде**. Эта ADR не
пересматривает то решение и не создаёт исключения для Яндекс-провайдера:
`YandexMusicSourceProvider` обязан резолвить обе стороны co-appearance-пары
в реальный Genius id **до** того, как отдать `ProviderEdge` — артист,
которого он не может уверенно сопоставить с Genius-артистом, в ребро
просто не попадает (та же честная семантика "не найдено", что и у
Genius-провайдера, что и в игре по ADR-0009). Иными словами: **Яндекс —
источник РЁБЕР, не источник идентичности** — второе id-пространство не
появляется нигде в системе, ни временно, ни постоянно.

## Последствия

**Плюсы:**
- Единственная точка отказа Genius для *дефолтного* графа устранена —
  Яндекс недоступен → автоматический честный fallback на Genius, без
  ручного вмешательства и без изменения контракта для клиента.
- Логика "кто первый, кто резервный" — конфигурируемый список, не
  захардкоженный if/else в `CollabService` — порядок и состав провайдеров
  меняются в `static_config.yaml` без пересборки логики.
- Провайдеры независимо unit-тестируемы фейками (SF-TST-04) — не нужен
  ни Postgres, ни реальный HTTP до Яндекса/Genius, чтобы проверить сам
  алгоритм fallback.

**Минусы / цена:**
- Роль на Яндекс-рёбрах всегда `"feature"` — менее выразительно, чем
  Genius-кредиты; продукт должен объяснять пользователю разницу (или дать
  углубление по запросу — см. `docs/architecture/sequences/deepen-on-demand.md`,
  SF-YM-03) вместо того, чтобы делать вид, что вся ролевая информация
  доступна сразу.
- Два независимых внешних API означают два независимых режима отказа,
  которые нужно понимать по отдельности при инцидентах — `EdgeSource`
  на каждом ребре существует именно для того, чтобы это было видно
  наблюдателю/логам, а не только конечному провайдеру.
- На момент принятия этой ADR (см. `docs/architecture/sequences/build-default-graph.md`)
  `MusicSourceProviderChain` полностью реализован и протестирован, но
  публичный путь `/api/v1/graph` (`CollabService::BuildRadialGraph`) ещё
  не переведён на него — цена промежуточного состояния, не решения самой
  ADR; зафиксировано честно, а не скрыто.
