# ADR-0011: Абстракция MusicSourceProvider — Яндекс дефолт/обязателен, Genius — углубление и fallback

## Статус

Принято (SF-ARCH-02, Release 0.8). Опирается на
[ADR-0009](./0009-canonical-artist-identity-in-game.md) (каноническая
идентичность артиста) и [ADR-0001](./0001-split-into-four-services.md)
(разбиение на сервисы) — не заменяет ни одно из них.

**Частично устарело**: Яндекс.Музыка как второй провайдер удалена целиком
из системы — см. «Addendum: удаление Яндекс.Музыки как источника графа» в
конце файла. Абстракция `MusicSourceProvider`/`MusicSourceProviderChain`
(разделы ниже) остаётся в силе как есть.

## Контекст

До Release 0.8 единственным источником рёбер графа коллабораций был
Genius: `CollabService` ходил напрямую в `GeniusGatewayClient`, который
ходил в `six-feat-genius-gateway`. Genius API кредитует роли (primary/
producer/writer/featured), но у него собственные rate-limit'ы и
доступность — единственная точка отказа для *всего* графа, не только для
углублённых данных.

**Разворот 2026-07-27**: Яндекс.Музыка (реверс-инженеренный API,
`six-feat-yandex-gateway`, SF-YM-01) становится **дефолтным и обязательным**
источником рёбер для *дефолтного* графа — не опциональным дополнением "на
будущее". Причина: co-appearance артистов на треке Яндекс отдаёт дёшево и
без per-user OAuth (сервисный токен на весь деплой), тогда как Genius
несёт более богатую ролевую гранулярность (producer/writer/featured), но
дороже по rate-limit'ам и требует более тяжёлого клиента (уже
централизованного в genius-gateway). Разумно развести ответственность:
Яндекс — *ширина* графа (кто с кем вообще пересекался), Genius —
*глубина* (какая именно роль) плюс страховка на случай, если Яндекс
недоступен.

Технически нужна была абстракция, за которой CollabService не знает,
какой конкретно апстрим дал ребро — иначе логика fallback/переключения
размазалась бы по вызывающему коду, а не жила бы в одном месте.

## Решение

1. **Интерфейс `MusicSourceProvider`** (`libs/six-feat-common`):
   `GetCollaborationEdges(seed, user_token) → vector<ProviderEdge>`.
   `ProviderEdge{from, to, source, role}` — оба конца ребра уже
   **реальные Genius id** (см. «Явная связь с ADR-0009» ниже), `source`
   (`EdgeSource::YandexFeature`/`GeniusCredit`) — аудит-метаданные о том,
   КАКОЙ провайдер отдал ИМЕННО ЭТО ребро, не второй ключ идентичности.
2. **Два провайдера, оба реализуют интерфейс** (`services/six-feat/src/infrastructure`):
   `YandexMusicSourceProvider` (обёртка над `six-feat-yandex-gateway`,
   сервисный токен, `role` всегда `"feature"` — это всё, что физически
   даёт co-appearance) и `GeniusMusicSourceProvider` (обёртка над
   `GeniusGatewayClient`, полная ролевая гранулярность).
3. **Провайдер, который не может достучаться до апстрима (rate-limit,
   circuit open, сеть), БРОСАЕТ исключение**, а не молча возвращает пустой
   список — иначе "Яндекс сказал: рёбер нет" неотличимо от "Яндекс
   недоступен", а это два разных случая с разной обработкой.
4. **`MusicSourceProviderChain`** — компонент-композиция, пробует
   провайдеров по порядку из `static_config.yaml` (`providers:` список,
   дефолт `[yandex, genius-fallback]`), первый успех — результат; если все
   бросили — честно пробрасывает последнюю ошибку выше (`TryProvidersInOrder`,
   `libs/six-feat-common`, пер функция, юнит-протестирована в SF-TST-04
   фейками успешного/падающего провайдера без сети).
5. **Никакой новой колонки/enum `provider` в БД** — `ProviderEdge.source`
   существует только на уровне возвращаемых данных провайдера
   (presentation/observability), не персистится как часть идентичности
   артиста или связи.

### Явная связь с ADR-0009 — почему идентичность НЕ меняется

[ADR-0009](./0009-canonical-artist-identity-in-game.md) фиксирует: **реальный
Genius id — единственный канонический ключ артиста, везде**. Эта ADR не
пересматривает то решение и не создаёт исключения для Яндекс-провайдера:
`YandexMusicSourceProvider` обязан резолвить обе стороны co-appearance-пары
в реальный Genius id **до** того, как отдать `ProviderEdge` — артист,
которого он не может уверенно сопоставить с Genius-артистом, в ребро
просто не попадает (та же честная семантика "не найдено", что и у
Genius-провайдера, что и в игре по ADR-0009). Иными словами: **Яндекс —
источник РЁБЕР, не источник идентичности** — второе id-пространство не
появляется нигде в системе, ни временно, ни постоянно.

## Последствия

**Плюсы:**
- Единственная точка отказа Genius для *дефолтного* графа устранена —
  Яндекс недоступен → автоматический честный fallback на Genius, без
  ручного вмешательства и без изменения контракта для клиента.
- Логика "кто первый, кто резервный" — конфигурируемый список, не
  захардкоженный if/else в `CollabService` — порядок и состав провайдеров
  меняются в `static_config.yaml` без пересборки логики.
- Провайдеры независимо unit-тестируемы фейками (SF-TST-04) — не нужен
  ни Postgres, ни реальный HTTP до Яндекса/Genius, чтобы проверить сам
  алгоритм fallback.

**Минусы / цена:**
- Роль на Яндекс-рёбрах всегда `"feature"` — менее выразительно, чем
  Genius-кредиты; продукт должен объяснять пользователю разницу (или дать
  углубление по запросу — см. `docs/architecture/sequences/deepen-on-demand.md`,
  SF-YM-03) вместо того, чтобы делать вид, что вся ролевая информация
  доступна сразу.
- Два независимых внешних API означают два независимых режима отказа,
  которые нужно понимать по отдельности при инцидентах — `EdgeSource`
  на каждом ребре существует именно для того, чтобы это было видно
  наблюдателю/логам, а не только конечному провайдеру.
## Статус реализации (обновлено SF-ARCH-03)

На момент принятия ADR цепочка была реализована и протестирована, но
единственным её потребителем оставалась internal-ручка
`POST /internal/music-source/collaboration-edges`: публичный путь
`/api/v1/graph`, углубление и фоновое обогащение держали
`GeniusGatewayClient` напрямую. Это состояние было зафиксировано здесь
честно и закрыто тикетом SF-ARCH-03. Что изменилось:

- **`MusicSourceProvider` расширен до song-level.** Топологического
  `GetCollaborationEdges` (только `from`/`to`/`source`/`role`) недостаточно
  для дефолтного графа: `BuildGraphJson` считает по трекам вес ребра,
  `dominant_role` и список `collaborations`. Добавлен
  `GetArtistSongs(seed, songs_limit, lane, user_token) -> ArtistSongs`.
  `lane` в сигнатуре обязателен — фоновое обогащение не должно занимать
  foreground-полосу рейт-лимита, за которой стоит очередь живых запросов.

- **`CollabService::FetchFg` и `EnrichmentWorker` переведены на цепочку.**
  Оба реальных потребителя графа ходят одним путём — Яндекс основной,
  Genius fallback. Порядок провайдеров в `static_config.yaml` обоих
  сервисов обязан совпадать, иначе кэш, который наполняет воркер,
  расходился бы по источнику с тем, что отдаётся пользователю.

- **Провайдеры вынесены в `libs/six-feat-sources`.** Раньше они лежали
  внутри `services/six-feat/src/infrastructure/`, из-за чего фоновый
  `six-feat-enrichment` физически не мог ими воспользоваться — это и была
  настоящая причина хардкода на Genius в воркере, а не недосмотр.

- **`GraphDeepenHandler` намеренно оставлен на прямой инъекции
  `GeniusMusicSourceProvider`.** Углубление по запросу — это и есть «дай
  ролевые кредиты Genius поверх дефолтного графа»; пропускать его через
  цепочку значило бы уронить его в Яндекс, у которого ролей нет.

- **Фан-аут по деталям треков переехал в `GeniusMusicSourceProvider`**, но его
  ограничитель — общий на сервис компонент `fg-fanout-limiter`
  (`libs/six-feat-core`), а не собственный семафор провайдера. В ту же
  foreground-полосу гейтвея фанится второй потребитель,
  `CollabService::CheckDirectPath`; пока у каждого был свой лимит с дефолтом 6,
  суммарный потолок клиента составлял 12 при `lane-fg-max-concurrent: 8` у
  гейтвея. Обещание схемы «stay at or under the gateway's own lane» держалось
  на честном слове и ломалось молча, стоило появиться второму потребителю.
  Один лимитер на одну полосу делает инвариант выражаемым в конфиге и
  независимым от числа потребителей.

### Идентичность трека: почему яндексовые id сдвинуты

`songs.id` — единое `BIGINT`-пространство на все источники, а Genius song id и
Яндекс track id нумеруются независимо с единицы. Проверено против схемы:
`postgresql/migrations/V1__initial_schema.sql` объявляет
`songs(id BIGINT PRIMARY KEY)` и `credits.song_id BIGINT REFERENCES songs(id)`,
и это единственная миграция, которая трогает `songs` — то есть отдельного
пространства идентификаторов на источник в схеме нет и не появлялось позже. Запись сырого яндексового id в ту же колонку — это
`ON CONFLICT (id) DO NOTHING` поверх чужой песни: заголовок остался бы
генисовым, а `credits` привязались бы к чужому треку. Поэтому яндексовые
id уводятся в старший бит (`kYandexSongIdOffset = 1 << 62`); реальные
Genius id (~1e7) до него не достают. Артистов это не касается — соартисты
и так резолвятся в настоящий Genius id (ADR-0009).

Побочная выгода: происхождение ребра восстановимо из самого `song_id`, без
миграции схемы и без второго сетевого вызова. `LoadNeighbours` выводит
`EdgeSource` прямо в SQL (`bool_and`), поэтому источник переживает запись в
Postgres и последующее чтение из кэша. Ребро считается яндексовым, только
если **все** общие треки пришли из Яндекса; смешанный случай честнее
подписать `genius_credit` — там роли богаче.

Как следствие, `DeriveEdgeSource`, выводивший источник из строки
`dominant_role` (`dominant_role == "feature"` → `yandex_feature`), удалён:
он врал на генисовых рёбрах с ролью `featured`. `EdgeSource` теперь берётся
из данных, а не угадывается по роли.

### Пустой ответ провайдера — не отказ

`TrySongsProvidersInOrder` отличается от топологического
`TryProvidersInOrder`: пустой результат тоже приводит к переходу на
следующего провайдера. Артиста может не быть на Яндексе — это законный
ответ, но отдать пользователю пустой граф вместо генисовского значило бы
потерять данные, которые раньше были.

При этом ошибка пробрасывается наверх только если **ни один** провайдер не
смог ответить. «Яндекс упал, а Genius честно сказал, что песен нет» — это
пустой граф, а не `502`: иначе артист без коллабораций превращался бы в
ошибку из-за сбоя соседнего провайдера.

### Известное свойство: лимитер углубления ключуется по токену, не по человеку

`RateLimitKey` в `graph_deepen_handler.cpp` возвращает `access_token` из
session-куки (`auth::ExtractToken`, `services/six-feat/src/token_router.hpp`), а
не устойчивый идентификатор пользователя вида `auth::StableUserId`. Значит
квота `20/мин` привязана к токену: новый токен — новое ведро, даже если за ним
тот же человек.

В проде это не эксплуатируется — токен живёт до конца сессии, и переполучение
его через OAuth дороже, чем подождать минуту. Но свойство реальное, и знать о
нём нужно в двух местах:

- **Тесты.** Общая сессионная фикстура `client` держит один токен на весь
  прогон, поэтому квоту углубления успевал выесть `test_contract_openapi.py`
  (schemathesis перебирает ручки и идёт раньше по алфавиту) — дипен-тесты
  получали `429` вместо ответа. Отсюда отдельная фикстура `deepen_client` со
  свежим токеном на тест: она проверяет углубление, а не рейт-лимит.
- **Если лимит когда-нибудь станет частью продуктового контракта** (квоты по
  тарифу и т.п.), ключ придётся сменить на `StableUserId` — иначе «20 в минуту
  на пользователя» будет неправдой. Сейчас формулировка честная только как
  «20 в минуту на сессию».

## Addendum: удаление Яндекс.Музыки как источника графа

Весь разворот «Яндекс — дефолт, Genius — fallback», описанный выше и
углублённый в [ADR-0013](./0013-two-provider-artist-identity.md) (namespaced
id + `artist_alias`), был откачен. Удалены целиком:
`six-feat-yandex-gateway`, `libs/six-feat-yandex`, `YandexMusicSourceProvider`,
namespaced Yandex artist/song id, таблица `artist_alias` (миграция V11), 422
на графе/пути возвращён к историческому поведению SF-YM-08 (см. тот тикет:
резолв уже известного из кэша артиста не требует Genius-токена, резолв
нового имени/id — требует).

**Что осталось от этого ADR:** сама абстракция `MusicSourceProvider` +
`MusicSourceProviderChain` (`ReorderProvidersPreferring`,
`TryProvidersInOrder`, честный fallback через исключение, а не пустой
список) — низкорисковый, уже протестированный механизм, не имеющий смысла
выбрасывать вместе с конкретным вторым провайдером, которого он
обслуживал. Сегодня `static_config.yaml` обоих сервисов (`six-feat`,
`six-feat-enrichment`) конфигурирует цепочку единственным элементом:
`providers: [genius-fallback]`. `EdgeSource` в `libs/six-feat-common`
сократился до одного значения (`kGeniusCredit`) — второй элемент
(`kYandexFeature`) и связанный с ним `DiscoverySource` удалены как мёртвый
код, а не оставлены про запас.

Раздел «Известное свойство: лимитер углубления ключуется по токену, не по
человеку» выше не затронут этим откатом — углубление всегда было
Genius-only и осталось им.
