# ADR-0012: six-feat остаётся основным публичным сервисом данных — без отдельного BFF

## Статус

Принято (по факту с [ADR-0001](./0001-split-into-four-services.md),
формализовано в SF-DOC-04 как самостоятельная запись, поскольку решение
не проговаривалось явно раньше).

## Контекст

В системе пять userver-сервисов (`six-feat`, `six-feat-auth`,
`six-feat-enrichment`, `six-feat-genius-gateway`, `six-feat-game`) и один
`nginx` перед тремя из них (`six-feat`, `six-feat-auth`, `six-feat-game`
— см. `docs/architecture/c4-container.md`). Топология шире, чем один
сервис — естественный вопрос: не пора ли перед ней поставить отдельный
API Gateway/BFF-сервис, который агрегирует вызовы к
`genius-gateway`/`enrichment`/`auth` и отдаёт фронтенду единый,
скрывающий внутреннюю топологию контракт?

Сегодня эту роль частично играет `nginx` (единый публичный порт,
path-based роутинг на три из пяти сервисов), но `nginx` — конфигурация,
не код: он не агрегирует ответы нескольких сервисов в один, не хранит
состояние, не принимает решений — чистый reverse proxy.

## Решение

**Не вводить отдельный BFF/API Gateway сервис. `six-feat` остаётся
основным публичным сервисом данных и точкой оркестрации для доменной
области "граф коллабораций"; `nginx` остаётся тонким path-based роутером,
не более.**

Конкретно:

1. **`six-feat` уже оркестрирует то, что нужно оркестрировать в его
   собственном домене**: `CollabService` внутри `six-feat` сам решает,
   когда идти в `ArtistRepository` (Postgres), когда — в
   `GeniusGatewayClient`/`MusicSourceProviderChain` (`genius-gateway`),
   когда поставить фоновую задачу в `EnrichmentClient` (`enrichment`).
   Отдельный BFF перед `six-feat` был бы вторым слоем той же самой
   оркестрации — сетевой хоп без новой бизнес-логики.
2. **`six-feat-auth` и `six-feat-game` — намеренно отдельные публичные
   поверхности**, не спрятанные за `six-feat` — см.
   [ADR-0004](./0004-auth-service-local-session-verification.md) (сессия
   проверяется локально в каждом из трёх сервисов, никогда не идёт за
   подтверждением по сети) и
   [ADR-0007](./0007-game-mode-as-separate-service.md) (game — отдельный
   сервис намеренно). Проксировать их через `six-feat` вместо `nginx`
   означало бы либо (а) `six-feat` начинает знать про game/auth-специфичную
   логику, которой ADR-0004/0007 явно её лишили, либо (б) чистый
   passthrough без добавленной ценности — то же самое, что уже делает
   `nginx`, но кодом, а не конфигом.
3. **`nginx` решает только "один origin для браузера"** — задачу, которая
   существует из-за того, что фронтенд использует относительные пути
   (`fetch("/auth/me")`, `window.location.href = "/auth/login"`) и не
   должен знать, какой из трёх контейнеров реально ответит. Это не BFF по
   определению: BFF агрегирует/трансформирует данные под конкретный
   фронтенд, `nginx` здесь — нет.
4. **`six-feat-genius-gateway` намеренно НЕ публичен** (см.
   `docs/architecture/c4-container.md`) — он уже выполняет роль
   внутреннего шлюза для конкретного домена (rate-limit + CircuitBreaker
   к одному внешнему API), а не общего API Gateway для всей системы; это
   разные ответственности, которые не стоит сливать в один сервис.

## Последствия

**Плюсы:**
- Один сетевой хоп меньше на горячем пути (`/api/v1/graph`,`/path`,
  `/search`) — задержка не растёт на ровном месте ради топологии, которая
  сама по себе ничего не решает.
- Session-verification остаётся строго локальной в каждом из трёх
  публичных сервисов (ADR-0004) — BFF, который терминировал бы
  auth/сессию сам, конфликтовал бы с этим решением или дублировал бы его.
- Меньше сервисов для деплоя/мониторинга/патчинга по сравнению с
  вариантом "ещё один Gateway сверху".

**Минусы / цена:**
- Фронтенд обязан знать о path-based контракте `nginx`
  (`/auth/*` → auth, `/api/v1/game/*` → game, всё остальное → six-feat) —
  это распределённое знание живёт в `nginx/default.conf.template`, не в
  одном явном OpenAPI-контракте одного сервиса. Расхождение между
  реальными роутами сервисов и `nginx`-конфигом — не автоматически
  ловится (см. `docs/DEVELOPMENT.md` «Паритет docker-compose между
  окружениями», SF-CFG-02 — но это про паритет dev/staging/prod, не про
  путь-контракт).
- Если публичная поверхность вырастет ещё (седьмой/восьмой сервис со
  своим набором маршрутов) — решение стоит пересмотреть: у `nginx` нет
  предела, но agregating-логика на клиенте ("собери мне данные из трёх
  сервисов одним вызовом") рано или поздно перевесит цену лишнего хопа.
  Эта ADR не запрещает завести BFF в будущем — она фиксирует, что три
  path-based маршрута через `nginx` этого ещё не оправдывают.
