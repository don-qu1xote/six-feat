# ADR-0004: Вынести OAuth-флоу в six-feat-auth, но проверять сессию в six-feat локально

## Статус

Принято (IDEA-53).

## Контекст

OAuth-хендлеры (`LoginHandler`/`CallbackHandler`/`LogoutHandler`/
`MeHandler`) изначально жили внутри `six_feat`. Решено вынести весь
OAuth 2.0 Authorization Code Flow (редирект на Genius, обмен `code` на
`access_token`, PKCE, шифрование сессии, установка/сброс cookie
`six_feat_session`) в отдельный сервис `six-feat-auth`
(`services/auth/`, порт 8083) — по тем же соображениям изоляции
жизненного цикла и секретов, что и остальные разрезы (см. ADR-0001).

Отдельный, более узкий вопрос внутри этого разреза: как `six_feat`
проверяет сессию на каждый входящий запрос к `/api/v1/graph`/`path`/
`search`/`status`/`sse`? Два варианта:

1. HTTP-вызов к `six-feat-auth` на каждый запрос данных, чтобы
   подтвердить валидность cookie.
2. Расшифровать cookie локально в `six_feat`, тем же `APP_SECRET`,
   которым `six-feat-auth` её зашифровал.

Вариант 1 добавляет сетевой round-trip **на каждый** хендлер данных —
латентность и ещё одну точку отказа для самого частого пути в системе.

## Решение

`RequireSession`/`ExtractToken` (`services/six-feat/src/auth/
token_router.hpp`) расшифровывают cookie `six_feat_session` локально в
процессе `six_feat`, используя `session_crypto::KeyFromEnv()` — тот же
`APP_SECRET`, которым `six-feat-auth` шифрует сессию при логине.
`six_feat` **не делает HTTP-вызов** к `six-feat-auth` на проверку
сессии — расшифровка остаётся O(1)-операцией в процессе, без сетевого
хопа на горячем пути.

Прямое следствие: оба сервиса обязаны быть запущены с одинаковым
`APP_SECRET` — иначе `six_feat` не расшифрует cookie, выданную
`six-feat-auth` (и наоборот). До SF-SEC-01 рассинхрон `APP_SECRET`
проявлялся только как молчаливый 401 на каждый аутентифицированный
запрос, без какой-либо диагностики.

Закрыто в SF-SEC-01: `AppSecretParityChecker`
(`services/six-feat/src/auth/app_secret_parity_checker.hpp`) периодически
сверяет необратимый fingerprint `APP_SECRET` этого процесса с тем, что
публикует `six-feat-auth` на `GET /internal/key-fingerprint` — сам
секрет по сети не передаётся. Рассинхрон логируется громко (один раз, на
переходе) и отражается в `/readyz` (`app_secret_parity`-проверка → 503).
Недоступность `six-feat-auth` сама по себе НЕ валит readiness — та же
мягкая посадка, что у genius-gateway/enrichment (см. ADR-0001/0002/0003).

## Последствия

**Плюсы:**
- Проверка сессии на самом частом пути в системе остаётся O(1),
  без сетевой зависимости от доступности `six-feat-auth`.
- `six-feat-auth` может быть временно недоступен (деплой, рестарт) без
  единого 5xx на существующих аутентифицированных сессиях.

**Минусы / цена:**
- `APP_SECRET` — общий секрет двух сервисов, который может молча
  разойтись (ротация на одном без другого, опечатка в переменной
  окружения); митигировано, но не устранено полностью,
  `AppSecretParityChecker`-ом (детектирует с задержкой в один цикл
  проверки, не мгновенно).
- `GENIUS_CLIENT_ID`/`GENIUS_CLIENT_SECRET` всё ещё должны быть заданы и
  на `six_feat` тоже (для валидации конфига при старте), хотя реальный
  OAuth-обмен ими больше не пользуется — источник путаницы при настройке
  окружения.
