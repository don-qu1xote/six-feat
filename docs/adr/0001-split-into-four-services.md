# ADR-0001: Разбить six-feat на четыре независимых сервиса

## Статус

Принято (IDEA-25, IDEA-45, IDEA-53).

## Контекст

Изначально `six_feat` был одним процессом: HTTP-хендлеры, фоновый глубокий
скан коллабораций (`EnrichmentWorker`), обращение к Genius API
(`GeniusGateway` — CircuitBreaker + FG/BG rate-limiting) и весь OAuth-флоу
(`LoginHandler`/`CallbackHandler`/`LogoutHandler`/`MeHandler`) жили в одном
бинарнике, на одних task processor'ах, с одним процессом деплоя и
рестарта.

У этих четырёх кусков функциональности разный профиль нагрузки и разный
жизненный цикл:

- HTTP-хендлеры графа/пути/поиска обслуживают синхронный пользовательский
  трафик и должны отвечать быстро.
- Фоновый скан (IDEA-25) — долгие, низкоприоритетные задачи, не связанные
  с конкретным HTTP-запросом; их отказ не должен трогать пользовательский
  трафик, и наоборот — сбой основного процесса не должен обрывать фоновый
  скан на середине.
- Выход в Genius API (IDEA-45/46) — единственный внешний сетевой
  ресурс с общим лимитом на аккаунт/токен; CircuitBreaker и rate-limiting
  имеют смысл только если они общие для ВСЕГО исходящего трафика, а не
  раздельные копии state в каждом процессе, который решил постучаться в
  Genius.
- OAuth-флоу (IDEA-53) — редкие, разовые вызовы логина/логаута, отдельная
  зона ответственности за секреты (`GENIUS_CLIENT_SECRET`) и PKCE.

## Решение

Разбить на четыре независимо деплоящихся userver-сервиса из одного
репозитория (`docker-compose.yml` поднимает все четыре, у каждого свой
Dockerfile `target`):

| Сервис | Порт | Отвечает за |
|---|---|---|
| `six-feat` | 8080 | HTTP-хендлеры графа/пути/поиска/статуса + локальная проверка сессии |
| `six-feat-enrichment` | 8081 | Фоновый глубокий скан (IDEA-25) |
| `six-feat-genius-gateway` | 8082 | Весь исходящий трафик к Genius API (IDEA-45/46) |
| `six-feat-auth` | 8083 | OAuth 2.0 Authorization Code Flow (IDEA-53) |

Общий код (домен, resilience-примитивы, Postgres-слой, инфраструктура
схем) вынесен в `libs/six-feat-common`, подключаемую через
`add_subdirectory()` — не отдельно собираемую библиотеку, а общий
исходник для всех четырёх `CMakeLists.txt`.

Конкретное обоснование каждого отдельного разреза — в ADR-0002
(enrichment), ADR-0003 (genius-gateway) и ADR-0004 (auth).

## Последствия

**Плюсы:**
- Каждый сервис можно рестартовать/скейлить/деплоить независимо (фоновый
  скан не блокирует выкладку хендлеров и наоборот).
- Один источник истины для Genius-лимитов вместо N независимых копий
  CircuitBreaker/rate-limiter.
- Меньше поверхность секретов на процесс: `GENIUS_CLIENT_SECRET` нужен
  только `six-feat-auth`, `ENRICHMENT_INTERNAL_SECRET` — только сервисам
  внутренней сетки.

**Минусы / цена:**
- Внутренний HTTP-слой между сервисами (`X-Internal-Secret`-gated) —
  дополнительная сетевая связь, которой не было в монолите; контракт
  зафиксирован и покрыт тестами (см. `tests/test_contract_gateway.py`,
  SF-TST-01).
- `docker-compose.yml` и four `static_config.yaml` должны согласованно
  обновляться при любом изменении, затрагивающем более одного сервиса
  (порты, секреты, схема БД) — источник практических регрессий в течение
  разработки (см. `scripts/verify-yaml-anchors.py` как один из способов
  ловить рассинхрон).
- `APP_SECRET`/схема Postgres — общие ресурсы между сервисами, которые
  расходятся молча, если их не проверять явно (см. ADR-0004).
