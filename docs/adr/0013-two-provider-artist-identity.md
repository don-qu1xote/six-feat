# ADR-0013: Двупровайдерная идентичность артиста — namespaced Yandex id + artist_alias

## Статус

Принято (Release 1.2, SF-ARCH-04/05/06). Опирается на
[ADR-0009](./0009-canonical-artist-identity-in-game.md) (каноническая
идентичность в игре) и [ADR-0011](./0011-music-source-provider-abstraction.md)
(абстракция MusicSourceProvider) — расширяет оба, не отменяет ни один.

## Контекст

`YandexMusicSourceProvider` (ADR-0011) физически не мог обслуживать
Yandex-only пользователя: `ResolveToGeniusArtist()` на каждое имя
со-артиста из Яндекса ходило в Genius API за реальным Genius id — то есть
даже «яндексовый» путь тайно требовал Genius-токен. Артист, которого
Genius не знал (а каталог Яндекса по СНГ-сцене заметно шире), тихо
выбрасывался. У сервиса при этом нет собственного Genius-токена вообще —
Genius всегда только BYO-пользовательский, — а Яндекс работает на едином
сервисном токене. Асимметрия аутентификации уже была устроена ровно так,
как нужно; мешала только жёсткая привязка идентичности узла графа к
Genius-id-пространству.

## Решение

**Namespaced Yandex artist id + таблица `artist_alias`, канонизация на
чтении (не физическая перезапись строк).**

1. **`NamespacedYandexArtistId`/`IsYandexArtistId`**
   (`six-feat-common/music_source_provider.hpp`) — зеркало уже принятого
   для треков `NamespacedYandexSongId` (ADR-0011/SF-ARCH-03): старший бит
   (`1<<62`) метит id как принадлежащий Яндекс-пространству в общем BIGINT
   `artists.id`. `YandexMusicSourceProvider` больше не зовёт Genius вообще
   — со-артист строится напрямую из данных Яндекса.
2. **`artist_alias(provider, provider_artist_id, canonical_artist_id)`**
   (V10) — связывает id в пространстве провайдера с каноническим
   `artists.id`. Genius каноничен, когда известен (богаче: роли, url,
   popularity); namespaced Yandex id каноничен сам по себе, пока связки
   нет.
3. **Канонизация на ЧТЕНИИ, не на записи.** `SongsForArtist` и
   `LoadNeighboursImpl` (`persistent_store.cpp`) делают `LEFT JOIN
   artist_alias` и группируют/джойнят по `COALESCE(canonical_artist_id,
   raw_id)`. Строки `credits`/`songs` под сырым Yandex-id НЕ
   переписываются и не удаляются — они остаются собственной историей
   записи этого id навсегда; связка просто говорит читающему запросу «а
   ещё это тот же человек, что и...». Это осознанное отклонение от
   первоначального наброска тикета (который предполагал идемпотентную
   физическую перезапись `credits` с `ON CONFLICT DO NOTHING`): join на
   чтении не нуждается в идемпотентной перезаписи вообще, потому что
   ничего не переписывается — вставка одной строки в `artist_alias`
   (`ON CONFLICT (provider, provider_artist_id) DO NOTHING`) тривиально
   идемпотентна сама по себе.
4. **`ProviderCredentials`.** Вместо нового типа, оборачивающего голый
   `user_token` во всех сигнатурах цепочки (что потребовало бы менять
   контракты `MusicSourceProvider`/`CollabService`/каждого хендлера),
   принято более узкое решение: `GeniusMusicSourceProvider` и
   `EnrichmentWorker.EnqueueIfNeeded` сами трактуют пустой `user_token` как
   «этот провайдер не обслужит запрос» — молча возвращают пусто вместо
   похода в сеть и WARNING-лога. Тот же практический эффект (Genius
   пропускается без ошибки, не роняя запрос), меньшая площадь изменения.
5. **Отказ от 422.** `graph_handler.cpp`/`path_handler.cpp` перестали
   требовать Genius-токен — дефолтный граф и поиск пути работают на одном
   Яндексе. `graph_deepen_handler.cpp` **сохраняет** свой 422: «найти
   больше связей» органически Genius-only (роли producer/writer/mixer
   Яндекс физически не отдаёт) — это не ограничение по инерции, а
   свойство данных.
6. **Честная деградация.** Каждый узел графа несёт `deepen_available`
   (`!IsYandexArtistId(id)` — после п.3 уже канонизированный id, так что
   связанный через alias узел автоматически даёт `true`). Кнопка «найти
   больше связей» отражает это состояние заранее, не после проваленного
   клика.

## Явная связь с ADR-0009

Сохранено полностью: резолв на вводе, никаких синтетических id в
состоянии, честная ошибка вместо заглушки. Расширено: «канонический id»
теперь означает «Genius, если известен; иначе id собственного
провайдера», а не «всегда Genius». Namespaced Yandex id — **не** тот же
класс проблемы, что `synthId()` из ADR-0009: `synthId()` — временная,
ничего не значащая метка для *неразрешённого* имени; namespaced id —
реальный, стабильный, внешне проверяемый идентификатор уже **разрешённого**
артиста, просто в другом пространстве. См. дополнение 2026-08 в ADR-0009.

## Явная связь с ADR-0011

`MusicSourceProvider`/`MusicSourceProviderChain` не изменились по форме
(п.4 выше — сознательно более узкое решение, чем полный
`ProviderCredentials`). Пропуск провайдера из-за отсутствия токена — это
теперь явно «этот провайдер не обслуживает» (тихо, DEBUG-уровня по духу),
а не «провайдер упал» (WARNING) — разница в намерении, если не всегда в
буквальном уровне лога на каждом call-site.

## Последствия

**Плюсы:**
- Yandex-only пользователь получает полноценный граф/путь/фоновое
  обогащение без единого Genius-токена.
- Артист, которого Genius не знает (шире CIS-каталог Яндекса), больше не
  выбрасывается молча — попадает в граф как полноценный узел.
- Один и тот же реальный артист, известный обоим провайдерам, — один узел
  в графе, а не два (при наличии `artist_alias`-связки).
- Вес ребра (`SF-DB-09`) больше не задваивается, когда одна и та же
  коллаборация известна обоим провайдерам (дедуп по нормализованному
  названию трека, а не по `song_id`) — исправлено и в
  `LoadNeighboursImpl`, и в `graph_handler.cpp`'s собственной агрегации.

**Минусы / принятый долг:**
- **Лениво-фоновая связка (`artist_alias` заполняется автоматически, когда
  у пользователя есть Genius-токен и в графе встретился неразвязанный
  Yandex-узел) НЕ реализована в этом проходе.** Таблица и канонизация на
  чтении работают корректно с уже существующими связками, но сегодня
  строки в `artist_alias` появляются только вручную/административно.
  Без этой фоновой задачи дубли узлов (один реальный человек под двумя
  id) не схлопнутся сами — они просто не будут возникать чаще, чем сейчас
  (Yandex-only и Genius-only пользователи и так видели разные графы).
  Follow-up, не потеря функциональности относительно состояния до этого
  ADR.
- **Полная канонизация ВСЕХ точек входа id в игровое состояние не
  сделана.** `/internal/neighbours` (единственный существующий мост
  игра↔граф) канонизирует на чтении бесплатно, как следствие п.3 — это
  единственная гарантия, которая реально проверена тестами
  (`tests/test_artist_alias.py`). Админ-публикация дейли и
  пользовательский `POST /challenge` берут id из других источников
  (случайный выбор по графу, пользовательский ввод) и сегодня НЕ проходят
  через канонизацию явно. Риск материализуется только вместе с
  предыдущим пунктом (без фоновой связки `artist_alias` пуста в
  реалистичном дев-окружении) — но это открытый пробел, не забытый
  случай, и самая рискованная зона всего релиза (см. SF-GAME-23) требует
  отдельного прохода, когда фоновая связка появится.
- Углубление (`graph_deepen_handler.cpp`) остаётся Genius-only навсегда —
  это свойство данных (роли), не временное ограничение.

## Обновление docs/architecture/

`docs/architecture/sequences/build-default-graph.md` и C4-диаграммы
описывают путь построения графа как Yandex+Genius-fallback (ADR-0011) —
после этого ADR путь для Yandex-only пользователя (без Genius-токена
вообще) идёт по цепочке идентично, просто без второго (Genius) плеча
цепочки когда-либо активируясь; отдельной новой диаграммы не требуется,
т.к. форма цепочки не изменилась (см. «Явная связь с ADR-0011» выше) —
изменилось только то, что раньше отсутствие Genius-токена было ошибкой,
а теперь — нормальный режим.
